# Roadmap

What Fearlezz is for, where it stands and where it is going. Read this first when picking up the work, and update it in the same change that moves something.

Last updated: 2026-11-28.

## Purpose

AI does so much now that we need a much better way to manage it, so it can actually prove its work is good and useful, not "trust me, bro".

Fearlezz is one excellent tool that helps AI coding agents audit, verify and prove that their work is right, for any kind of project, locally and in CI. Media proof was the first use, not the limit.

## What shapes every decision

- **The agent uses it too.** It is not only a report for the developer. The agent reaches for it while working ("how does this look again?", "what did I need?").
- **Three intake points.** `fearlezz` (see), `fearlezz run` and `fearlezz say`, plus `fearlezz setup`. Everything else is discovered through `next:` and `fix:` lines.
- **Layers.** Turn on, tune, combine, own check, piece in the repo, piece from someone's repo, new kind of proof. Each layer is built from the one below, so new capabilities should be new layers, not new systems.
- **Proof is what can be seen, not what is said.** Checks that ran, their results, pictures and films. What the agent says about its own work never counts as proof.
- **All proof groups matter:** honest, does what was asked, did not break anything, tests are real, built well, safe. Not every project needs all of them.
- **Local first.** Journals and results live on the developer's machine. The final stage proves everything fresh once.
- **CI trusts only what it saw.** Local proof is the agent's word, so it never counts as proof in CI. CI proves the commit itself, and "ready to merge" is never said about work that has not been proven.
- **Free and paid.** Everything local is the open core in `crates/`. Hosted, paid parts go under `ee/`.

## Built

| Capability | Notes |
| --- | --- |
| Checks, stages | Proof is about behaviour, never files: any change needs every check not on a schedule, and a pass counts only for the inputs it ran on (every file outside `no_proof`, or the check's own `inputs`, a speed hint), so an edit to prose reruns nothing; the final stage runs everything fresh. Glob lists take `!` globs back out, the last match deciding. A check runs at the root, in the folder its `dir` names, or with `each` once in every project folder (`<check>/<folder>`; a Cargo project is a manifest no workspace above names a member); a folder that goes takes its checks with it |
| Results by input hash | Shared across worktrees, pruned after 30 days. A built in check (settings, rules, commits) is keyed on what the binary ships, a digest of its source, presets and skill made at build time, not its version, so two development builds of one version never share or contradict its results |
| Journals | One per piece of work, append only; `fearlezz --all` prints every journal as text |
| Command line | See, run, say, setup. A tool a check cannot find is named with how to install it; tools in `node_modules/.bin` and `.venv/bin` are found, those of a check's `dir` first. A word it does not know names this binary's version and path, since an older Fearlezz may come first on PATH; `setup sync` names every older `fearlezz` on PATH, and a session start hook that fails tells the agent so in its own format. Once a day it asks the proof host for the newest release and the lowest version the host takes (`GET /api/v2/cli`, never on CI, with the host off or with `FEARLEZZ_NO_UPDATE_CHECK`); `fearlezz` and a session start then tell the agent to update and tell the developer. Every call names its version in its `User-Agent`, and a host refuses runs from a CLI below its `CLI_MINIMUM` (`426`), which the CLI says with a `fix:` line while its checks still run. A failed check whose `run` joins commands with `&&` is told to list them as steps |
| Starting out | `SETUP.md`, linked from the top of the README with the line to paste into any coding agent, has it install Fearlezz the way the project installs its tools, check `which -a fearlezz` for an older copy first on PATH, then follow `fearlezz setup guide`: the full guide, embedded in the binary (`skills/fearlezz/GUIDE.md`) so it matches the installed version. It learns the project, finds what proves work today (CI on any system, git hooks, task runners, screenshot and coverage setups, pull request checklists), asks the setup kind (proof host, CI only, local only) and whether to take each existing system over so nothing runs twice, inits and shapes the checks to the commands the project really runs, syncs, gets the first proof green without weakening a check, offers what it could prove next and hands off through a pull request. It names kinds of tools with varied examples, never one stack. Without `fearlezz.toml`, every command leads to `fearlezz setup guide` and `fearlezz setup init`, which writes a starter from the languages at the root (Rust also from Cargo projects in folders, Dart and Flutter from pubspecs in folders), `no_proof` for prose and `fearlezz = "<its version>"`, the lowest Fearlezz the config needs (a piece may pin one too): an older binary refuses every command that reads the config, naming the version it needs, its own and its path, before a newer field or piece can confuse it. Nothing raises the pin by itself; lowering it weakens nothing, since it says which binary reads the config, no behaviour. In a repository on GitHub with no workflow proving with Fearlezz, its `next:` asks the agent to ask the developer whether CI sends its proof to the proof host: `setup init --ci host` (adding `id-token: write` and naming the GitHub App's install link, or whether it is installed when signed in) or `--ci plain` (which also writes `[host] off = true` into `fearlezz.toml`, adding it to one that is there) writes `.github/workflows/proof.yml` (`devenv: true` with devenv; a newer push cancels only a pull request's run, never a push to the base branch), keeps a `fearlezz.toml` that is there, and never writes over a workflow; every `next:` of it ends with `fearlezz setup sync`. A prerelease is older than its release, and `setup init` pins this binary's release part |
| Growing the proof | What a project could prove but does not yet: a UI (React, Vue, Svelte, Solid, Qwik, Next, Tauri, Flutter in any folder, Xcode or SwiftUI; the Xcode projects Flutter generates in an app's `macos` and `ios` folders, a workspace member's or an example app's too, are the Flutter app's, not an Apple app) no check takes stills or films of, rendered output (kustomize, helm, flate, terraform) no check keeps as texts, pictures the README does not show. `setup init` prints each in one `could prove:` line and asks the agent to offer them; while working the `settings` check gives one as a hint when the change touches files of its kind (rendered files only in the folders the rendering checks render from, never under `.github`), off per rule under `[lints.fearlezz]` and never above a hint; which of those files the change touches is part of the check's reuse key, and it reads only the files of kinds it could offer. The skill's "Grow the proof" teaches offering them. The README hint teaches `fearlezz setup showcase` and names the host's stable showcase addresses (`https://fearlezz.seamlezz.net/showcase/<owner>/<repo>/<check>/<picture>`), and a README linking them or the host counts as shown |
| Findings | Only lines the change touched can block |
| Test counts | A check's `tests` reader (JUnit reports, or a pattern in the output) counts what ran; zero tests fails it. Every language piece runs and counts its tests |
| Failed and flaky tests | A failed check names each test that failed, from its JUnit reports or a `failed` pattern beside its `count` (the rust and go pieces set one), in `fearlezz run`, the job summary, `proof.json` and on the host page, with what a failed pattern's test printed (after cargo's header line, before go's result line) under its name in the first three of those; a test named as failed fails the check even when the runner exits 0. The runner reruns, Fearlezz reads it: a test whose report holds `<flakyFailure>` or `<flakyError>` (Playwright with `includeRetries`, nextest, Maven) passed only on a rerun, which fails the check like a failure unless the check's `flaky_tests` names it; a listed one passes, shown apart, and listing it weakens the floor. Vitest and Jest write only the final result, and cargo test and go test do not rerun |
| Rules | Paths, naming, companion files, ast-grep code rules, files `.sops.yaml` names being encrypted |
| Settings | One source written into each tool's own file, drift is a finding. A lint table is written only for a tool a check reads the findings of, so a framework piece's rules for one linter leave no file in a project that runs another. A biome.json no piece configures and no check runs is named by `setup sync` and the settings check (a gate when Fearlezz wrote it, a hint otherwise), the way up from before Biome left the typescript piece |
| Agent skill | Embedded in the binary; `fearlezz setup sync` writes it for Claude Code (`.claude/skills`) and other agents (`.agents/skills`) in every project, unless it opts out. A missing or stale copy is led to by a `next:` line and is a finding of the `settings` check |
| Pieces | Rust, TypeScript (tsc; `svelte` puts svelte-check in its place), with the linters and formatters as pieces of their own: Biome, ESLint, oxlint (every rule at the level inferred from the decided ESLint and Biome rules, `docs/drive/language-pieces/oxlint-levels.tsv`), Prettier; `setup init` picks the ones package.json depends on, Biome when it names none. React, Next, Qwik, Solid and Vue pieces hold each framework's rules for Biome and oxlint, which `setup init` adds from package.json with either; the `settings` check names one a project's package.json depends on whose rules it lacks, and a biome.json left by the typescript piece of before. The tests come with a Vitest, Bun or Node test runner piece, which `setup init` picks from package.json and the lockfile. Playwright, Python, Go (with `go-race` at merge and `envtest`, whose Kubernetes binaries Fearlezz fetches for the version go.mod requires; `setup init` adds it for controller-runtime), Kotlin, Dart (`dart`, which `flutter` builds on, their checks in every pubspec folder no other one holds; `setup init` tells them apart by the Flutter SDK in pubspec.yaml), Lua (StyLua), devenv, infrastructure (kustomize and helm per folder, flux through flate, both validated by kubeconform; terraform and opentofu validate per initialised folder; nix flake check; yamllint, which writes `.yamllint.yaml`; sops, a rule from `.sops.yaml` that never decrypts; `setup init` adds each from the files its tool reads, flux instead of kustomize in a Flux repository), agents, commits (Conventional Commits: the pull request title, in CI or from `gh` locally, else every commit since the base), safety, trufflehog, betterleaks, osv-scanner, actions; pinned with `fearlezz.lock`. Checks are named for their tools (`vitest`, `ruff`, `go-test`), so language pieces combine; Rust keeps `fmt`, `clippy`, `tests`. |
| Stills and films | Compared with the same check run on the base commit, checked out in the user cache folder (outside the repository, so dev servers serve it). `fearlezz run` and `fearlezz` name each picture that is not the same with its comparison and the paths of its before and after files, for the agent to read; there is no local page (only the host has one). Changed pictures never hold the work: the final stage says how many changed (and apart, how many could not be compared) and that a person reviews them on the pull request. Compared per color channel by one Rust function (`crates/fearlezz-compare`, no I/O, built for wasm too): a film is read as its own `yuv420p` planes at its own size and the comparison converts them to colour (BT.601) and scales them (by area, films at 720p at most), so every machine and ffmpeg build gives the same result; stills arrive as RGB at their own size. Listed in `proof.jsonl` or found by `stills` and `films` globs, a film's name keeping its extension so a still and a film of one screen never share verdicts or notes, and two pictures of one name fail the check; `flaky` pictures show apart and are not counted as changed. The `playwright` piece takes them from `toHaveScreenshot` and videos, its `webServer` on the free port every run gets (`FEARLEZZ_PORT`) |
| Film marks | A check says what happened in a film with `mark` and `span` lines in `proof.jsonl` (seconds into the film, or the wall clock with a `start` line, which Fearlezz's own recorder writes), and the film is timed from them: after each mark its timing must match (strict), a `free` span (a load, a fade, a spinner) may take any time and look any way, only the state it ends on compared (a film's last state always), and is no anchor, so films may have more or fewer; a said moment may read a tenth of a second late; a film whose marks differ is changed, and one without marks is timed from its start. The marks cut both films into sections and a state is matched only within its own section; the same sections are the comparison's `timeline`, on which the page plays both films aligned at their marks, a film with no footage in a stretch of half a second or more holding its frame under a grey veil labelled "No footage" (no outlines there), its lane hatched there; a shorter stretch holds its frame quietly, since showing it would only flicker. The CLI, CI's comparison with the approved picture and the page's wasm comparison all time from them; the page draws shown marks as ticks and free spans as hatched bands on each film's lane, and names the step the playhead is in. This project's Playwright films mark every key and pointer press, their loading, and as `settling` free spans every stretch where anything animates or a part is `aria-busy`, with `start` at the page's first painted frame (`ee/app/e2e/marks.ts`); `test.step` and `performance.mark` as sources come later |
| Texts | Rendered text a check writes (manifests, a plan), named by a `texts` glob or `"kind": "text"` in `proof.jsonl`, compared line by line with the same check run on the base commit and reviewed like a picture: `fearlezz run` and `fearlezz` print its summary, its before and after files and the start of its diff; the job summary folds the diff under it; the bundle keeps it as `.txt`, which the proof host serves as plain text, shows as a diff and takes verdicts and whole text notes on |
| Generated code | `generates` globs on the check that runs a generator: the files they name must come out of its command the same as the tree had them, or the check fails with the diff and leaves the regenerated files to commit; no `git diff` glue. Narrowing it weakens the proof |
| Recording app windows | macOS, in the binary (ScreenCaptureKit via objc2): `fearlezz --still <window>` for the agent to look at its running app, and `record` on a check films or stills the first window that appears after its command starts, and stops a command that runs `wait` without one; the stills on request keep the newest 20. Where nothing can record it fails locally with the one time fix and is not run in CI. `flutter-look` piece: headless widget test stills, and integration test films of one entry file on macOS and (off by default) on an iOS simulator; an app in a folder names it in each check's `dir`, and the helpers follow the stills check's folders (each one with `each`), also while it is off |
| Recording beyond macOS windows | A check that `needs = ["ios"]` leases a booted iOS simulator of Fearlezz's own (`fearlezz <device type> <n>`, locked per run, kept booted, a run's apps removed and the keychain reset before and after) and gets its id in `FEARLEZZ_DEVICE`; `needs = ["linux"]` starts Xvfb on a display it picks and hands it in `DISPLAY`. With `record` they film or still the first app or window that appears (`simctl io`; the window's pixels over X into ffmpeg), with no Screen Recording, on CI's runners too. A machine that can never have the screen leaves the check to CI and does not hold the work; a runner of the right system without the tool fails. Measured on GitHub's macOS runners: a new device boots in 81 to 182 s and stays busy with its first launches for minutes more, in which a film took up to 28 s to start, so a film gets 60 s. The flutter-look piece's `flutter-phone-film` films its integration test on one (off by default). Not yet: a film per test case (clips) |
| Recording off the developer's screens | Opt in per machine with `FEARLEZZ_OFF_SCREEN=1`: the recorded window is parked in a screen corner as soon as it appears (window capture still records all of it, and a parked Flutter app keeps drawing), and focus goes back to the developer's app if the recorded one took it while it settled. AeroSpace parks it when it runs (floating on a workspace it does not show), Accessibility otherwise; where neither can, the log says why and it records where it opened. No virtual display and no private API. New windows are watched for through the window server's list (about 2 ms a listing, every 10 ms; ScreenCaptureKit, about 70 ms a listing, only captures), so the window shows where it opened for about 0.12 s by Accessibility and 0.2 to 0.45 s by AeroSpace (which picks windows up on its own schedule, over 2 s on a loaded machine; recording waits for it up to 3 s, so the film starts on the window's final size, since AeroSpace tiles a window it picks up and parking floats it; later than that it records anyway, parking goes on for up to 10 s, and the log says when the size changed during the film; proven at load 400 to 560), since macOS lets no app place another's new window. On plain macOS a strip of about 40 by 32 points stays in a bottom corner with no other display beyond it. Window positions the app saved while parked (macOS saves them on every move) are put back once the command ends, so it does not reopen in the corner; only positions parked during the run are touched, so the developer's own moves and a parallel recording stay, and after a killed run the next one clears the parked position. Fearlezz sends the app no input: its own test drives it. Proven on the developer's machine with a native and a Flutter app, AeroSpace on and off, in 14 runs (drive record `docs/drive/off-screen-recording.md`) |
| Scheduled proof | A check too slow, costly or reliant on real infrastructure to run for each change has `schedule = true`: no change needs it (locally or in `run --ci`), `fearlezz --plan` lists it apart, naming it runs it, and `fearlezz run --ci --scheduled` proves only those, from a scheduled workflow (the action's `scheduled` input). The action's `issue-on-failure` opens one issue for a failed proof, or comments on the open one: the action's only write to GitHub, asked for by the project. Putting a check on a schedule weakens the proof; scheduled checks keep their own floor |
| Machine wide heavy queue | Opt in per machine with `FEARLEZZ_QUEUE=<slots>` (off by default and wherever `CI` is set): a check's command, a run on the base commit (look's before, red before green) and a picture comparison each take one of that many slots first, whichever worktree or repository they come from, so many agents on one machine queue instead of all starting at once. The number is the developer's, not counted from cores, since every heavy tool already uses all of them; 1 is one at a time. A slot is a `flock`ed file in the user cache folder holding who has it, so a waiter prints once `wait <step>: the heavy queue is full (...); behind <step> in <worktree> (pid, time)` and how its wait ended, and a holder that dies frees it. A waiting check whose inputs another worktree proves meanwhile reuses that result instead of running. A check can say `light = true` to never wait, not for its command, its run on the base commit or its picture comparison; the built in checks never wait. A run waiting for its worktree's services, which another run there holds, says so too; the services always come before a slot, so a run waiting for them holds none. A `FEARLEZZ_QUEUE` that is no number above zero says the queue is off instead of quietly ignoring it. A tool run by hand queues with `fearlezz run -- <command>`, which exits with the command's code and shows the agents waiting behind it only its program (`behind cargo by hand in ...`); a Fearlezz inside a held slot runs at once under it instead of waiting on itself. Waiters poll, so the next turn goes to whichever polls first, not the longest waiting |
| Safety | Pieces to pick from, each a check named for its tool: `safety` (gitleaks, the default every starter gets), `trufflehog` and `betterleaks` for secrets (gate on changed lines, never printed or stored), `osv-scanner` for vulnerable dependencies (flag, counted when the change touched the lockfile), `actions` (zizmor over GitHub workflows, its own levels). Read natively, without shell glue |
| Environments | Fresh checkout setup, services with their own ports per worktree |
| Secrets | A check names the secrets it needs (`secrets = ["EVAL_API_KEY"]`); Fearlezz takes each from its own environment when it is set there (so CI's own tokens need no setup) and asks SecretSpec for the others, one name at a time, in the `[env] shell` with its own variables, so the provider's token (1Password's `OP_SERVICE_ACCOUNT_TOKEN` in CI) never reaches the check. Values are masked as `***` in every text file a run keeps, shows or uploads (as they are, as JSON escapes them and line by line; values under 4 characters are not), and only the names key reuse; a run on the base commit that could not get a secret is not reused. One SecretSpec cannot give fails the check with the fix, without running it, and never makes it unstable. Changing a check's secrets weakens the proof, as its `env` does. Every command the config names (a check's, envtest's, each `[env]` command, a release place's publish and landed) is one `Command` (steps, folder, `env`, `secrets`, budget) run by one runner, so they all get secrets, a clean environment and masking the same way; `[env] secrets` reach only the preview. OIDC credentials (GCP for terraform plan) still reach a check through `env` |
| Preview deploys | A service that lives remotely: `[env] preview` deploys the checkout (in the `[env] shell` with a clean environment like a check's, the `[env] secrets` masked in its log, and `FEARLEZZ_PREVIEW_NAME`, the branch made safe for a URL, `pr-<number>` for a pull request in CI, `commit-<sha>` when detached, `base-<tree>` for the base) and prints its URL; a check with `needs = ["preview"]` gets the last URL printed as `FEARLEZZ_PREVIEW_URL`. Once per tree per checkout, the base under the checkout lock; a preview that fails or prints no URL fails each check that needs it, without running it, with the fix. Looks deploy the base the same way. `run --ci` names the URL in the job summary and `proof.json`, and the proof host links it on the work's page and in its one pull request comment (no other write to GitHub). Changing `preview` or `secrets` weakens the proof |
| Distribution | GitHub Releases for Linux and macOS through release-please (merging its pull request tags and builds), `install.sh`, Homebrew tap, Nix flake and devenv input, `cargo install --git`. Windows is served through WSL, not natively: devenv, which most projects' checks run in, needs Nix, which runs on Windows only inside WSL. The release workflow writes the tap's formula after it attaches the binaries (a deploy key on the tap, `HOMEBREW_TAP_DEPLOY_KEY`); rebuilding an older tag leaves the tap alone |
| CI for other projects | `fearlezz-dev/fearlezz@v0`, a small composite action that installs the release of its tag, or the lowest version `fearlezz.toml` pins when that is newer (a pin in either quotes, refused when it is no version; `version: installed` older than the pin fails the step), runs `fearlezz run --ci --proof <dir>` and keeps the proof bundle and check logs as artifacts. Free CI only proves: it writes nothing to GitHub unless the project asks for `issue-on-failure` (see Scheduled proof), writes the job summary (proven or not, blockers, checks, failing output, changed pictures for a person to review on the pull request, each weakening as a diff of its part of the config), installs a pinned static ffmpeg on Linux when checks record pictures and neither the project's `[env]` shell nor PATH has one (Fearlezz runs the ffmpeg it compares, records and draws with by the absolute path it found once per run, in the project's shell first, locally too, and with a check's clean environment, so the project's ffmpeg never sees Fearlezz's own secrets), and fails on a weakening everywhere (an admin can merge past the required check). The human gate is GitHub's own pull request review. A proof splits over several jobs: `[platform.<name>]` names a runner (its OS, values for setup steps) and a check's `on` the platforms it must pass on, its `job` a leg of its own and its `timeout` a budget for all its steps and its recording, past which it is stopped and fails. `--plan` prints the legs for `matrix.include`, each leg (`--leg`) runs its checks, and the gate (`--gate`) combines their bundles into one proof and one job summary, the required check; a leg that did not finish is not proven, dropping a platform weakens the proof, and a pull request reuses a pass its base commit's proof shows for the same inputs on the same platform (a push proves everything fresh). The action takes `plan`, `leg` and `gate`, and a reusable workflow (`.github/workflows/prove.yml`) wires all three. Locally a check runs once, unless every platform it is on names another OS. Fearlezz proves itself through this action, split into a Linux and a macOS leg, with `contents: read`, `actions: read` and `id-token: write` only. Tested against a fake GitHub API that records every request, to show no write is made; the issue step is checked by actionlint and zizmor only |
| Hosted proof (`ee/`) | The proof host, redesigned (`docs/drive/hosted-redesign.md`): it draws a live page of each work itself and is the authority for review. `fearlezz run --ci` streams its run by protocol version 2 of `ee/README.md` (open, each check's start and end with its files and look, done with `proof.json`) from GitHub Actions with `id-token: write` once the app is installed, prints the page URL, and never fails the proof over a host error; a job on GitHub Actions without `id-token: write` says in its log and job summary why it sent nothing (not a fork's pull request, which never gets the token), a repository with `[host] off = true` sends nothing and never mentions the page, and `setup login` says whether the app is installed on the repository it runs in. The page (a Solid app in `ee/app`, redesigned in `docs/drive/page-design/record.yaml`) leads with one status strip (its word, what it waits on, a bar while checks run), shows each failed check first with why it failed, what to do, its failed tests, its findings and its output folded, folds the checks that passed, opens a run proved in legs on the leg whose pictures wait, shows each screen once with a swatch per viewport and theme, folds each weakening behind Show change with a word diff of its part as the base and the change have it, and shows runs and checks live through one Durable Object per work, and every picture as it arrives with five ways to compare, films on one clock, flaky pictures marked; pictures load only from a separate files origin under an hour long grant. A signed in writer says per picture "Looks right" (kept by content, so it carries over to later pushes, and a picture that changed since its looks right or its note is marked Look again (a film as a still); the page opens on the first picture to look at again, else the first that waits; Looks right resolves the picture's open notes; the page then moves on to the next picture that waits, and stepping keeps the picture in place; Undo takes it back, as does Looks right pressed again; keys for all of it, listed under ?; full screen with the review beside the picture, and zoom by pinch, ⌘ scroll or keys, both sides on one view that stays on the screen's other variants), drags a region on a picture's before, after or both to leave a note (one on another variant of the screen is offered again, in its place when the pictures are the same size, or only its words, and kept linked to it), which makes the picture need change until it is resolved, edits a note's words (one Save, on every note linked with it unless unchecked; a note's words grow to six lines), and resolves notes, each shown at once and taken back if the host refuses (the Worker and its rooms run beside D1, so a write no longer crosses the world twenty times); every film moves on the page's own clock, a click on it plays or pauses (in full screen a film stepped to plays at once), a drag notes the frame it paused on, it plays slower or faster (¼× to 4×, < and >), and a screen's films are swatches of its tile before its stills; a film's looks right also says it of the still of its viewport and theme, and a held Y (or the arrow beside Looks right) opens a board of the screen's variants, each showing whether it waits, already looks right or has a note, where 1 to 4 pick a shape (this picture, its viewport, its theme, the whole screen), arrows and Space or a press and a sweep pick single tiles, and Y says it, counting what it marks and the notes it resolves; a note made on a picture that looks right takes the looks right back; full screen fits the window and never scrolls; the next pictures are fetched and decoded ahead (films fetched whole into the browser's cache), every frame takes its picture's own shape so notes land in the same place at any window size, and a picture swaps in only once decoded, so stepping never blanks or jumps; a check whose base has no pictures says so once above the sheet; a weakening fails the CI job as without a host until an admin accepts exactly it at that head on the page, which runs the failed job again through GitHub's API, and the job then asks the host and passes. The host writes one `Fearlezz review` check run and one pull request comment as the GitHub App from its webhooks; once every attempt of the head's proof workflows completed (none still queued or running), each leg without its proof is named with its cause and its job in one list: a leg whose runs all ended without done, a planned leg that opened no run, or, with no run of the head at all, the proof workflow (known by the `workflow` file a CI run names), so the review ends cancelled with what a person or an agent re-runs; the host runs nothing again. The gate of a split proof always opens and closes a run of its own, also when the plan left no leg, so a head whose plan reuses every pass is proven. A pull request closed while CI proves it still gets its check run finished, though its comment is no longer edited. The agent reads it through the CLI: `fearlezz setup login` (GitHub's device flow through the host, a token of the host's own that never gives a verdict), verdicts and open notes in `fearlezz`, `fearlezz --notes` with each region drawn, the stop hook held while notes are open. Once signed in, every `fearlezz run` streams as a local run, marked unproven, never reviewed, taking notes. A writer makes share links that show anyone the work's live page, view only, until revoked (the token kept as its HMAC). `/<owner>/<repo>` lists every work of a repository, newest activity first, with its state and what waits, live. ## Known problems

- **Self hosted runners that run several jobs of one attempt.** The host ties a GitHub job to its run by run id, attempt and runner; when one runner ran several jobs of an attempt and only one of them is known, a job that ends can cancel the other's run. GitHub's hosted runners run one job each, so it does not happen there. A queued job named with `name:` does not show as waiting for a runner.
- **Monorepos beyond Rust and Dart.** A check runs in every project folder with `each`, and the rust, dart and flutter pieces and `setup init` use it for Cargo projects and pubspecs; the other language pieces and `setup init` still look only at the repository root. A pub workspace's members inside a root package get no checks of their own, Dart's `analysis_options.yaml` is still written at the root only, and the flutter-look checks run at the root unless each names its folder in `dir`.
- **Films stop working until replayd restarts.** On the developer's machine, after a few dozen films (27 in one series, during a load spike), every film fails with "failure to process first sample buffer" while stills still work, with the 0.2.0 build as well; killing `replayd` (launchd restarts it) brings films back. Its cause is unknown. Every film is noted in the machine's film log (`films.jsonl` in Fearlezz's cache folder: repository, check, how it went, the `replayd` pid and the load), so how often it happens can be counted; failures in a row under one `replayd` pid are this problem.
- **Recording app windows is proven only on the developer's machine.** CI runs the proof on macOS too, but hosted runners cannot grant Screen Recording.
- **CI on macOS proves only the macOS code.** This repository's macOS leg lints the code only macOS compiles and runs the tests that reach it (`clippy/macos`, `tests/macos`), and only when those files change; a change elsewhere that behaves differently on macOS (BSD tools, a case insensitive file system) is first seen in the developer's local proof.
- **Linux only code is not proven locally.** The local proof runs on macOS, so code behind `cfg(not(target_os = "macos"))` is first linted in CI.
- **Native Windows jobs stay outside the proof.** Fearlezz runs on Windows only inside WSL, so a project that must build or test on native Windows (GrammarGuard's `flutter build windows` and `flutter test -d windows`) keeps those as plain CI jobs that its proof does not see.
- **CI pictures never ran in another project.** Fearlezz proves itself on GitHub's runners, but no other project uses the action's pictures yet.
- **Red before green costs are measured for Rust and Go only.** What running the base commit costs for TypeScript, Python, Kotlin and Flutter projects is not known.
- **Some page films still change between two runs of the same page.** Of 26 films, 5 changed in the last measurement (12 before the page look fixes, stills 0): a `<video>` the page plays (after Play, or a click) is no animation, so its playback is judged frame by frame; a settle's last frames can show later than its span allows when the machine is loaded; and one change in the failed run's output, before its press, has no known cause. The film pair's lanes test in `ee/app/e2e/compare.look.ts` fails about once in 24 runs, on main as well.
- **A flaky test.** One test in `core` has failed twice on CI and not locally; its name is still unknown. A failed test check now names each failed test (`failed: <name>`), so the next failure names it.
- **Any rebase needs a new comparison run.** A run's look and red before green verdict are kept per base commit (`AgainstBase`), though each depends only on the base run's inputs, so a rebase over a change outside a check's inputs (prose, for one) still makes the next run check out the base and compare again. Keying them by the base inputs, hashed from git blobs without a checkout, would remove that; its cost is not measured.
- **A local pull request title can be a minute old.** Locally the title comes from `gh pr view`, which takes most of a second over the network and runs on every `fearlezz` (each hook too) that hashes the `commits` check's inputs, so one answer is kept per branch for a minute in the user's cache folder. A renamed or newly opened pull request shows within that minute; nothing yet clears it sooner. With no answer kept, a run waits for `gh` up to five seconds (a slow network or GitHub) before it goes on without a title.
- **The default reuse key reads the whole tree.** A check without `inputs` hashes every file outside `no_proof` on each command (once per file, however many checks); the cost in a large repository is not measured. Git's blob ids for unchanged files would avoid reading them.
- **Part of the hosted review has met only the fake GitHub.** The device flow of `setup login`, notes and verdicts on real pictures, and an accept running a job again are proven under `wrangler dev --local` against a fake GitHub, not yet on GitHub itself.
- **A pull request proved by `workflow_dispatch` depends on the webhook.** Its run names no pull request (the release pull request is proved this way), so the host learns of the pull request only from the `pull_request` webhook; one sent while the host was down leaves the work without its check run until the pull request changes.
- **Forks are not hosted.** A pull request from a fork gets no OIDC token in its CI, so its run never reaches the host: no page, verdicts or check run. Its proof is the free one (the job and its summary).
- **A film's frames compare with codec tolerance.** A verdict carries over when the run finds its picture the same as the approved one. A still is compared exactly (antialiasing and fewer than 30 changed pixels aside), but a film's frames by the blurred diff with a threshold of 28 levels, which codec noise needs, so a faint change in a film can carry a looks right over.
- **A split proof has not run on GitHub yet.** Plan, legs and gate, the reuse of the base commit's proof through `gh run download`, and the reusable workflow are proven against local bundles; the first pull request of this repository after it merges is their first real run. The required check becomes the gate job `proof`; `proof-macos` is gone.
- **Reuse keys are computed on the plan's runner.** A check that lists `env` variables whose values differ between the plan's runner and its leg's never matches its base pass, so it always runs (never the other way round).
- **A repository's first proof cannot end without a run.** The host learns which workflow file proves from the `workflow` a CI run of it names, so until one reached the host, a head whose proof never reaches it keeps its review waiting for CI.
- **A webhook the host missed is not sent again.** A planned leg that opens no run ends with its workflow run attempt (the `workflow_run` webhook), and a run that never says done with its job (`workflow_job`); GitHub does not resend a delivery the host answered with an error, so while the host is down such a review can stay running until the proof runs again.
- **Renamed jobs are not matched.** The host knows a `workflow_job` runs Fearlezz when its name is the `GITHUB_JOB` of an earlier run; a job its workflow renames with `name:` is never matched, so it shows no "waiting for a runner" and its end does not cancel a run that never said done.
- **Sync never removes a setting a piece dropped.** Biome's `linter.rules` is written whole, so a dropped rule leaves `biome.json`; every other setting merges into the tool's file, so one a piece no longer sets (a tsconfig option, Biome's `files`, a clippy.toml key) stays there.
- **Secrets are fetched once per command.** Each named secret not set in Fearlezz's own environment is one `secretspec get` in the `[env] shell`, for every check, folder of an `each` check, base or red before green run, preview deploy and release place, so a check with two secrets over ten folders asks SecretSpec twenty times. Keeping the values in memory for one `fearlezz run` would ask once per name.
- **A note on a text is about the whole text.** The host takes no note on a line or a range of lines of a text's diff, and `fearlezz --notes` saves the noted text as it is.
- **About 40 lint flags** in the code, each left on purpose. They do not block: the `unsafe` blocks that call libc; indexing into serde_json values (which never panics) and toml_edit documents (guarded by a table check); wildcards over serde_json and toml values; saturating float casts in the recorders; the Linux recorder's screen and row indexing, bounded by construction; the protocol's event enums, whose shapes are the wire format; `Stages::first` and `Stages::name`; and four test assertions.

## Goldens

There are none, by decision: a look compares against the same check run on the base commit, so nothing goes stale. Tests generate their pictures and films when they run, and check command output with text matches. Texts follow the same decision: rendered output is compared with the base run, never with a committed golden.
