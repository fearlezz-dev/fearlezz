# Roadmap

What Fearlezz is for, where it stands and where it is going. Read this first when picking up the work, and update it in the same change that moves something.

Last updated: 2026-11-18.

## Purpose

AI does so much now that we need a much better way to manage it, so it can actually prove its work is good and useful, not "trust me, bro".

Fearlezz is one excellent tool that helps AI coding agents audit, verify and prove that their work is right, for any kind of project, locally and in CI. Media proof was the first use, not the limit.

## What shapes every decision

- **The agent uses it too.** It is not only a report for the developer. The agent reaches for it while working ("how does this look again?", "what did I need?").
- **Three intake points.** `fearlezz` (see), `fearlezz run` and `fearlezz say`, plus `fearlezz setup`. Everything else is discovered through `next:` and `fix:` lines.
- **Layers.** Turn on, tune, combine, own check, piece in the repo, piece from someone's repo, new kind of proof. Each layer is built from the one below, so new capabilities should be new layers, not new systems.
- **Proof is what can be seen, not what is said.** Checks that ran, their results, pictures and films. What the agent says about its own work never counts as proof.
- **All proof groups matter:** honest, does what was asked, did not break anything, tests are real, built well, safe. Not every project needs all of them.
- **Local first.** Journals and results live on the developer's machine. The final stage proves everything fresh once.
- **CI trusts only what it saw.** Local proof is the agent's word, so it never counts as proof in CI. CI proves the commit itself, and "ready to merge" is never said about work that has not been proven.
- **Free and paid.** Everything local is the open core in `crates/`. Hosted, paid parts go under `ee/`.

## Built

| Capability | Notes |
| --- | --- |
| Checks, stages | Proof is about behaviour, never files: any change needs every check not on a schedule, and a pass counts only for the inputs it ran on (every file outside `no_proof`, or the check's own `inputs`, a speed hint), so an edit to prose reruns nothing; the final stage runs everything fresh. Glob lists take `!` globs back out, the last match deciding. A check runs at the root, in the folder its `dir` names, or with `each` once in every project folder (`<check>/<folder>`; a Cargo project is a manifest no workspace above names a member); a folder that goes takes its checks with it |
| Results by input hash | Shared across worktrees, pruned after 30 days |
| Journals | One per piece of work, append only; `fearlezz --all` prints every journal as text |
| Command line | See, run, say, setup. A tool a check cannot find is named with how to install it; tools in `node_modules/.bin` and `.venv/bin` are found |
| Starting out | Without `fearlezz.toml`, every command leads to `fearlezz setup init`, which writes a starter from the languages at the root (Rust also from Cargo projects in folders) and `no_proof` for prose |
| Findings | Only lines the change touched can block |
| Test counts | A check's `tests` reader (JUnit reports, or a pattern in the output) counts what ran; zero tests fails it. Every language piece runs and counts its tests |
| Failed and flaky tests | A failed check names each test that failed, from its JUnit reports or a `failed` pattern beside its `count` (the rust and go pieces set one), in `fearlezz run`, the job summary, `proof.json` and on the host page; a test named as failed fails the check even when the runner exits 0. The runner reruns, Fearlezz reads it: a test whose report holds `<flakyFailure>` or `<flakyError>` (Playwright with `includeRetries`, nextest, Maven) passed only on a rerun, which fails the check like a failure unless the check's `flaky_tests` names it; a listed one passes, shown apart, and listing it weakens the floor. Vitest and Jest write only the final result, and cargo test and go test do not rerun |
| Rules | Paths, naming, companion files, ast-grep code rules, files `.sops.yaml` names being encrypted |
| Settings | One source written into each tool's own file, drift is a finding. A lint table is written only for a tool a check reads the findings of, so a framework piece's rules for one linter leave no file in a project that runs another |
| Agent skill | Embedded in the binary; `fearlezz setup sync` writes it for Claude Code (`.claude/skills`) and other agents (`.agents/skills`) in every project, unless it opts out. A missing or stale copy is led to by a `next:` line and is a finding of the `settings` check |
| Pieces | Rust, TypeScript (tsc; `svelte` puts svelte-check in its place), with the linters and formatters as pieces of their own: Biome, ESLint, oxlint (every rule at the level inferred from the decided ESLint and Biome rules, `docs/drive/language-pieces/oxlint-levels.tsv`), Prettier; `setup init` picks the ones package.json depends on, Biome when it names none. React, Next, Qwik, Solid and Vue pieces hold each framework's rules for Biome and oxlint, which `setup init` adds from package.json with either; the `settings` check names one a project's package.json depends on whose rules it lacks, and a biome.json left by the typescript piece of before. The tests come with a Vitest, Bun or Node test runner piece, which `setup init` picks from package.json and the lockfile. Playwright, Python, Go (with `go-race` at merge and `envtest`, whose Kubernetes binaries Fearlezz fetches for the version go.mod requires; `setup init` adds it for controller-runtime), Kotlin, Dart (`dart`, which `flutter` builds on; `setup init` tells them apart by the Flutter SDK in pubspec.yaml), Lua (StyLua), devenv, infrastructure (kustomize and helm per folder, flux through flate, both validated by kubeconform; terraform and opentofu validate per initialised folder; nix flake check; yamllint, which writes `.yamllint.yaml`; sops, a rule from `.sops.yaml` that never decrypts; `setup init` adds each from the files its tool reads, flux instead of kustomize in a Flux repository), agents, commits (Conventional Commits: the pull request title in CI, every commit since the base locally), safety, trufflehog, betterleaks, osv-scanner, actions; pinned with `fearlezz.lock`. Checks are named for their tools (`vitest`, `ruff`, `go-test`), so language pieces combine; Rust keeps `fmt`, `clippy`, `tests`. |
| Stills and films | Compared with the same check run on the base commit, checked out in the user cache folder (outside the repository, so dev servers serve it). `fearlezz run` and `fearlezz` name each picture that is not the same with its comparison and the paths of its before and after files, for the agent to read; there is no local page (only the host has one). Changed pictures never hold the work: the final stage says how many changed and that a person reviews them on the pull request. Compared per color channel; films at 720p at most, stills at their own size. Listed in `proof.jsonl` or found by `stills` and `films` globs; `flaky` pictures show apart and are not counted as changed. The `playwright` piece takes them from `toHaveScreenshot` and videos, its `webServer` on the free port every run gets (`FEARLEZZ_PORT`) |
| Texts | Rendered text a check writes (manifests, a plan), named by a `texts` glob or `"kind": "text"` in `proof.jsonl`, compared line by line with the same check run on the base commit and reviewed like a picture: `fearlezz run` and `fearlezz` print its summary, its before and after files and the start of its diff; the job summary folds the diff under it; the bundle keeps it as `.txt`, which the proof host serves as plain text, shows as a diff and takes verdicts and whole text notes on |
| Generated code | `generates` globs on the check that runs a generator: the files they name must come out of its command the same as the tree had them, or the check fails with the diff and leaves the regenerated files to commit; no `git diff` glue. Narrowing it weakens the proof |
| Recording app windows | macOS, in the binary (ScreenCaptureKit via objc2): `fearlezz --still <window>` for the agent to look at its running app, and `record` on a check films or stills the first window that appears after its command starts, and stops a command that runs `wait` without one; the stills on request keep the newest 20. Where nothing can record it fails locally with the one time fix and is not run in CI. `flutter-look` piece: headless widget test stills, and integration test films of one entry file |
| Recording beyond macOS windows | A check that `needs = ["ios"]` leases a booted iOS simulator of Fearlezz's own (`fearlezz <device type> <n>`, locked per run, kept booted, a run's apps removed and the keychain reset before and after) and gets its id in `FEARLEZZ_DEVICE`; `needs = ["linux"]` starts Xvfb on a display it picks and hands it in `DISPLAY`. With `record` they film or still the first app or window that appears (`simctl io`; the window's pixels over X into ffmpeg), with no Screen Recording, on CI's runners too. A machine that can never have the screen leaves the check to CI and does not hold the work; a runner of the right system without the tool fails. Not yet: a film per test case (clips), the flutter piece's checks for them, and the simulator on CI measured |
| Recording off the developer's screens | Opt in per machine with `FEARLEZZ_OFF_SCREEN=1`: the recorded window is parked in a screen corner as soon as it appears (window capture still records all of it, and a parked Flutter app keeps drawing), and focus goes back to the developer's app if the recorded one took it while it settled. AeroSpace parks it when it runs (floating on a workspace it does not show), Accessibility otherwise; where neither can, the log says why and it records where it opened. No virtual display and no private API. New windows are watched for through the window server's list (about 2 ms a listing, every 10 ms; ScreenCaptureKit, about 70 ms a listing, only captures), so the window shows where it opened for about 0.12 s by Accessibility and 0.2 to 0.45 s by AeroSpace (which picks windows up on its own schedule, over 2 s on a loaded machine; recording waits for it up to 3 s, so the film starts on the window's final size, since AeroSpace tiles a window it picks up and parking floats it; later than that it records anyway, parking goes on for up to 10 s, and the log says when the size changed during the film; proven at load 400 to 560), since macOS lets no app place another's new window. On plain macOS a strip of about 40 by 32 points stays in a bottom corner with no other display beyond it. Window positions the app saved while parked (macOS saves them on every move) are put back once the command ends, so it does not reopen in the corner; only positions parked during the run are touched, so the developer's own moves and a parallel recording stay, and after a killed run the next one clears the parked position. Fearlezz sends the app no input: its own test drives it. Proven on the developer's machine with a native and a Flutter app, AeroSpace on and off, in 14 runs (drive record `docs/drive/off-screen-recording.md`) |
| Scheduled proof | A check too slow, costly or reliant on real infrastructure to run for each change has `schedule = true`: no change needs it (locally or in `run --ci`), `fearlezz --plan` lists it apart, naming it runs it, and `fearlezz run --ci --scheduled` proves only those, from a scheduled workflow (the action's `scheduled` input). The action's `issue-on-failure` opens one issue for a failed proof, or comments on the open one: the action's only write to GitHub, asked for by the project. Putting a check on a schedule weakens the proof; scheduled checks keep their own floor |
| Machine wide heavy queue | Opt in per machine with `FEARLEZZ_QUEUE=<slots>` (off by default and wherever `CI` is set): a check's command, a run on the base commit (look's before, red before green) and a picture comparison each take one of that many slots first, whichever worktree or repository they come from, so many agents on one machine queue instead of all starting at once. The number is the developer's, not counted from cores, since every heavy tool already uses all of them; 1 is one at a time. A slot is a `flock`ed file in the user cache folder holding who has it, so a waiter prints once `wait <step>: the heavy queue is full (...); behind <step> in <worktree> (pid, time)` and how its wait ended, and a holder that dies frees it. A waiting check whose inputs another worktree proves meanwhile reuses that result instead of running. A check can say `light = true` to never wait, not for its command, its run on the base commit or its picture comparison; the built in checks never wait. A run waiting for its worktree's services, which another run there holds, says so too; the services always come before a slot, so a run waiting for them holds none. A `FEARLEZZ_QUEUE` that is no number above zero says the queue is off instead of quietly ignoring it. A tool run by hand queues with `fearlezz run -- <command>`, which exits with the command's code; a Fearlezz inside a held slot runs at once under it instead of waiting on itself. Waiters poll, so the next turn goes to whichever polls first, not the longest waiting |
| Safety | Pieces to pick from, each a check named for its tool: `safety` (gitleaks, the default every starter gets), `trufflehog` and `betterleaks` for secrets (gate on changed lines, never printed or stored), `osv-scanner` for vulnerable dependencies (flag, counted when the change touched the lockfile), `actions` (zizmor over GitHub workflows, its own levels). Read natively, without shell glue |
| Environments | Fresh checkout setup, services with their own ports per worktree |
| Secrets | A check names the secrets it needs (`secrets = ["EVAL_API_KEY"]`); Fearlezz asks SecretSpec for each, one name at a time, in the `[env] shell` with its own variables, so the provider's token (1Password's `OP_SERVICE_ACCOUNT_TOKEN` in CI) never reaches the check. Values are masked as `***` in every text file a run keeps, shows or uploads (as they are, as JSON escapes them and line by line; values under 4 characters are not), and only the names key reuse; a run on the base commit that could not get a secret is not reused. One SecretSpec cannot give fails the check with the fix, without running it, and never makes it unstable. Changing a check's secrets weakens the proof, as its `env` does. OIDC credentials (GCP for terraform plan) still reach a check through `env` |
| Preview deploys | A service that lives remotely: `[env] preview` deploys the checkout (in the `[env] shell` with a clean environment like a check's, the `[env] secrets` masked in its log, and `FEARLEZZ_PREVIEW_NAME`, the branch made safe for a URL, `pr-<number>` for a pull request in CI, `commit-<sha>` when detached, `base-<tree>` for the base) and prints its URL; a check with `needs = ["preview"]` gets the last URL printed as `FEARLEZZ_PREVIEW_URL`. Once per tree per checkout, the base under the checkout lock; a preview that fails or prints no URL fails each check that needs it, without running it, with the fix. Looks deploy the base the same way. `run --ci` names the URL in the job summary and `proof.json`, and the proof host links it on the work's page and in its one pull request comment (no other write to GitHub). Changing `preview` or `secrets` weakens the proof |
| Distribution | GitHub Releases for Linux and macOS through release-please (merging its pull request tags and builds), `install.sh`, Homebrew tap, Nix flake and devenv input, `cargo install --git`. Windows is served through WSL, not natively: devenv, which most projects' checks run in, needs Nix, which runs on Windows only inside WSL. The tap follows new releases once its workflow (tap pull request 1) is merged |
| CI for other projects | `fearlezz-dev/fearlezz@v0`, a small composite action that installs the release of its tag (and refuses one too old), runs `fearlezz run --ci --proof <dir>` and keeps the proof bundle and check logs as artifacts. Free CI only proves: it writes nothing to GitHub unless the project asks for `issue-on-failure` (see Scheduled proof), writes the job summary (proven or not, blockers, checks, failing output, changed pictures for a person to review on the pull request, each weakening as a diff of its part of the config), installs a pinned static ffmpeg when checks record pictures, and fails on a weakening everywhere (an admin can merge past the required check). The human gate is GitHub's own pull request review. A proof splits over several jobs: `[platform.<name>]` names a runner (its OS, values for setup steps) and a check's `on` the platforms it must pass on, its `job` a leg of its own and its `timeout` a budget past which it is stopped and fails. `--plan` prints the legs for `matrix.include`, each leg (`--leg`) runs its checks, and the gate (`--gate`) combines their bundles into one proof and one job summary, the required check; a leg that did not finish is not proven, dropping a platform weakens the proof, and a pull request reuses a pass its base commit's proof shows for the same inputs on the same platform (a push proves everything fresh). The action takes `plan`, `leg` and `gate`, and a reusable workflow (`.github/workflows/prove.yml`) wires all three. Locally a check runs once, unless every platform it is on names another OS. Fearlezz proves itself through this action, split into a Linux and a macOS leg, with `contents: read`, `actions: read` and `id-token: write` only. Tested against a fake GitHub API that records every request, to show no write is made; the issue step is checked by actionlint and zizmor only |
| Hosted proof (`ee/`) | The proof host, redesigned (`docs/drive/hosted-redesign.md`): it draws a live page of each work itself and is the authority for review. `fearlezz run --ci` streams its run by protocol version 2 of `ee/README.md` (open, each check's start and end with its files and look, done with `proof.json`) from GitHub Actions with `id-token: write` once the app is installed, prints the page URL, and never fails the proof over a host error. The page (a Solid app in `ee/app`, redesigned in `docs/drive/page-design/record.yaml`) leads with one status word, folds each weakening behind Show change with a word diff of its part as the base and the change have it, and shows runs and checks live through one Durable Object per work, and every picture as it arrives with five ways to compare, films on one clock, flaky pictures marked; pictures load only from a separate files origin under an hour long grant. A signed in writer says per picture "Looks right" (kept by content, so it carries over to later pushes), drags a region on a picture's before, after or both to leave a note, which makes the picture need change until it is resolved, and resolves notes; a weakening fails the CI job as without a host until an admin accepts exactly it at that head on the page, which runs the failed job again through GitHub's API, and the job then asks the host and passes. The host writes one `Fearlezz review` check run and one pull request comment as the GitHub App from its webhooks. The agent reads it through the CLI: `fearlezz setup login` (GitHub's device flow through the host, a token of the host's own that never gives a verdict), verdicts and open notes in `fearlezz`, `fearlezz --notes` with each region drawn, the stop hook held while notes are open. Once signed in, every `fearlezz run` streams as a local run, marked unproven, never reviewed, taking notes. A writer makes share links that show anyone the work's live page, view only, until revoked (the token kept as its HMAC). `/<owner>/<repo>` lists every work of a repository, newest activity first, with its state and what waits, live. Proven under `wrangler dev --local` against a fake GitHub and in headless Chrome (see Known problems) |

## Partly built

| Capability | Missing |
| --- | --- |
| Local and CI together | "Ready to merge" and the final exit code are honest. `fearlezz run --ci` proves a commit with no journal, runs every check not on a schedule, and holds a change to the base branch's config as its floor (what it weakens about the checks, never which files they read); `main` requires the check. A weakening fails the proof everywhere: locally, on any CI and on every pull request; an admin can merge past the required check. At the final stage `fearlezz` itself holds the work to the floor, so it never says ready while the change weakens the proof. CI writes the job summary (proven or not, each blocker with why and what to do, each weakening as a diff of the config, naming the head commit and the merge it proved, every check, its test count and the end of each failing output). Agent hooks (Claude Code, Codex, Cursor) refuse a pull request before ready and a merge past the required checks, block stopping once, and say a check's command run by hand is not proof. The Codex and Cursor hooks follow their docs but have not run in those agents yet, and they replace a project's own hooks for the same events in those files |
| Tests are real | Zero tests fails. Red before green runs the whole check on the base commit with the change's test files, in CI and at the final stage; a fix (its pull request title starts with `fix:`, or locally, without a title, any of its commits) blocks when it passes there or cannot run there. JUnit checks name the tests; a base that already fails shows nothing, and a check the change adds has nothing on the base to compare; every language piece sets `test_files` (Rust only `tests` folders). The verdict is kept with the run per base commit, beside its look, so `fearlezz` and the hooks hold the work to it too, and a rebase asks for a run again. Coverage: a test check's `coverage` (lcov, JaCoCo, Go coverprofile) finds each run of changed lines no test ran, test files aside; how strict follows the project's coverage against a target (80%): hints at or above it, under it flags when the change tests 80% of its lines and gates when not; the go, bun and flutter pieces measure it, rust, vitest, python and kotlin show the opt in line. The numbers show on the CI line, not yet in the proof bundle or on the host. No mutation proof |
| Releases as a layer | `[release.<place>]` holds a place's dry run (the check `release/<place>` at the last stage, held by the floor), its publish command and how to tell it landed; `fearlezz run --release` publishes where the version from the place's own file has not landed and waits until each place shows it, so running it again finishes a half done release. Pieces: crates, npm and pub (asked through their registries), github (built files on the release of the tag, landed by each file's SHA-256 digest). Missing: Homebrew, Nix, Scoop, winget, AUR, GHCR, Helm, Maven, Modrinth and Hangar pieces, an order between places (a tap after its release, a crate after the workspace crate it depends on, whose dry run on a release pull request cannot find the bumped version on crates.io yet), draft GitHub releases (the API answers a tag only for a published one), npm's trusted publishing (it reads GitHub's variables, which the clean env leaves out), release notes, and proof of the release in the job summary and on the proof host. Fearlezz's own release does not use it yet |
| Extension layers | Pieces work; a new kind of proof and a library layer do not exist yet |
| Hosted proof on real GitHub | Deployed, and `main` requires `Fearlezz review`. On this repository CI streams both jobs to the host, the live page shows them, the app's webhooks are received, and the app writes the check run and the comment. Not yet used on real GitHub: `setup login` (device flow), notes and verdicts on a pull request with pictures, and an admin's accept running the job again. See Known problems |

## Wishes

- **Faster film comparison.** A 94 second 1080p film took about 236 seconds. Timing from packets, a second read of state frames only, cheaper frame checks and comparing films at 720p at most cut the CPU time to less than half; on a 60 second 1080p film most of what is left is ffmpeg decoding it twice (the second read only picks state frames). Keeping state frames in memory would save that read at a cost in memory.

## Known problems

- **Self hosted runners that run several jobs of one attempt.** The host ties a GitHub job to its run by run id, attempt and runner; when one runner ran several jobs of an attempt and only one of them is known, a job that ends can cancel the other's run. GitHub's hosted runners run one job each, so it does not happen there. A queued job named with `name:` does not show as waiting for a runner.
- **Monorepos beyond Rust.** A check runs in every project folder with `each`, and the rust piece and `setup init` use it for Cargo projects; the other language pieces and `setup init` still look only at the repository root.
- **Films stop working until replayd restarts.** On the developer's machine, after a few dozen films (27 in one series, during a load spike), every film fails with "failure to process first sample buffer" while stills still work, with the 0.2.0 build as well; killing `replayd` (launchd restarts it) brings films back. Its cause is unknown. Every film is noted in the machine's film log (`films.jsonl` in Fearlezz's cache folder: repository, check, how it went, the `replayd` pid and the load), so how often it happens can be counted; failures in a row under one `replayd` pid are this problem.
- **Recording app windows is proven only on the developer's machine.** CI runs the proof on macOS too, but hosted runners cannot grant Screen Recording.
- **CI on macOS proves only the macOS code.** This repository's macOS leg lints the code only macOS compiles and runs the tests that reach it (`clippy/macos`, `tests/macos`), and only when those files change; a change elsewhere that behaves differently on macOS (BSD tools, a case insensitive file system) is first seen in the developer's local proof.
- **Linux only code is not proven locally.** The local proof runs on macOS, so code behind `cfg(not(target_os = "macos"))` is first linted in CI.
- **Native Windows jobs stay outside the proof.** Fearlezz runs on Windows only inside WSL, so a project that must build or test on native Windows (GrammarGuard's `flutter build windows` and `flutter test -d windows`) keeps those as plain CI jobs that its proof does not see.
- **CI pictures never ran in another project.** Fearlezz proves itself on GitHub's runners, but no other project uses the action's pictures yet.
- **Red before green costs are measured for Rust and Go only.** What running the base commit costs for TypeScript, Python, Kotlin and Flutter projects is not known.
- **A flaky test.** One test in `core` has failed twice on CI and not locally; its name is still unknown. A failed test check now names each failed test (`failed: <name>`), so the next failure names it.
- **Any rebase needs a new comparison run.** A run's look and red before green verdict are kept per base commit (`AgainstBase`), though each depends only on the base run's inputs, so a rebase over a change outside a check's inputs (prose, for one) still makes the next run check out the base and compare again. Keying them by the base inputs, hashed from git blobs without a checkout, would remove that; its cost is not measured.
- **The default reuse key reads the whole tree.** A check without `inputs` hashes every file outside `no_proof` on each command (once per file, however many checks); the cost in a large repository is not measured. Git's blob ids for unchanged files would avoid reading them.
- **Part of the hosted review has met only the fake GitHub.** The device flow of `setup login`, notes and verdicts on real pictures, and an accept running a job again are proven under `wrangler dev --local` against a fake GitHub, not yet on GitHub itself.
- **A pull request proved by `workflow_dispatch` depends on the webhook.** Its run names no pull request (the release pull request is proved this way), so the host learns of the pull request only from the `pull_request` webhook; one sent while the host was down leaves the work without its check run until the pull request changes.
- **Forks are not hosted.** A pull request from a fork gets no OIDC token in its CI, so its run never reaches the host: no page, verdicts or check run. Its proof is the free one (the job and its summary).
- **A changed film's verdict follows which states changed, not what they show.** Its bytes differ each time it is recorded, so its key is the comparison's shape (`review::key`): a verdict carries over when the same states change again, however differently. A tolerant digest of each state frame (the blurred, downscaled frame the comparison already reads) would make film verdicts follow content better. A new or gone film is keyed by its bytes, so its verdict never carries over.
- **A split proof has not run on GitHub yet.** Plan, legs and gate, the reuse of the base commit's proof through `gh run download`, and the reusable workflow are proven against local bundles; the first pull request of this repository after it merges is their first real run. The required check becomes the gate job `proof`; `proof-macos` is gone.
- **Reuse keys are computed on the plan's runner.** A check that lists `env` variables whose values differ between the plan's runner and its leg's never matches its base pass, so it always runs (never the other way round).
- **A planned leg that never opens keeps the host's review running.** The gate fails it on GitHub, but the host waits for a run of every planned leg; a leg cancelled before it started never opens one.
- **Renamed jobs are not matched.** The host knows a `workflow_job` runs Fearlezz when its name is the `GITHUB_JOB` of an earlier run; a job its workflow renames with `name:` is never matched, so it shows no "waiting for a runner" and its end does not cancel a run that never said done.
- **Sync never removes a setting a piece dropped.** Biome's `linter.rules` is written whole, so a dropped rule leaves `biome.json`; every other setting merges into the tool's file, so one a piece no longer sets (a tsconfig option, Biome's `files`, a clippy.toml key) stays there.
- **Secrets are fetched once per check run.** Each named secret is one `secretspec get` in the `[env] shell`, for every check, folder of an `each` check, and base or red before green run, so a check with two secrets over ten folders asks SecretSpec twenty times. Keeping the values in memory for one `fearlezz run` would ask once per name.
- **A note on a text is about the whole text.** The host takes no note on a line or a range of lines of a text's diff, and `fearlezz --notes` saves the noted text as it is.
- **About 85 lint flags** in the code, mostly possible panics from indexing, numeric casts in the recorder and long functions (`run_checks`). They do not block.

## Goldens

There are none, by decision: a look compares against the same check run on the base commit, so nothing goes stale. Tests generate their pictures and films when they run, and check command output with text matches. Texts follow the same decision: rendered output is compared with the base run, never with a committed golden.
