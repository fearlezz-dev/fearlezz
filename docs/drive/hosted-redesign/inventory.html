The host should own the review. CI should only prove.

Today CI owns everything a person sees: the page, the PR comment, the pictures and the approval state. The host is a file server with a bar on top. That is why the page cannot be live and feedback has nowhere to go.

What I found

The page URL already comes from the host. The real problem is that CI writes the HTML, so the host can only frame it.

What I propose

CI sends data and progress. The host draws a live page, records approvals and notes, and sets the GitHub check itself.

What you decide first

Whether free CI keeps approvals at all. It decides how much of the core gets deleted. Jump to it.

Today versus proposed

Today

Four writers to the PR, state hidden in a comment, a second workflow to react.

Proposed

One writer to the PR (the app). CI needs only id-token: write in hosted mode.

What hurts today

The page is frozen

CI writes index.html once, at the end. The host has no running or waiting state: a proof row is hidden until CI says done. No push, no poll anywhere.

Shell and frame fight

The page comes from CI, so it is untrusted. The bar above it must own every button; the page can only prefill words by postMessage. Two halves of one screen.

Approval is a comment

The host posts /fearlezz approve as you. A second workflow parses it, re-reads GitHub up to 4 times, guards ordering, and replies. Its state hides in a comment's hidden line.

No feedback channel

The only thing the agent can read back is an approval (say approve --github). No notes, no regions, no "not yet". Locally it is clipboard text.

Evidence, with file and line
  • Host has no live state: no Durable Object, queue or cron in ee/host/wrangler.toml; proofs hidden until done (ee/host/src/api.rs:208).
  • Page HTML built in CI as one string with inline script: crates/fearlezz/src/report.rs:825; prefill message: report.rs:751.
  • Shell frames the files origin: ee/host/src/pages.rs:413; view token: ee/host/src/approve.rs:151.
  • Hidden waiting line in the status comment: crates/fearlezz/src/github.rs:908; settle with retries: github.rs:581; ordering guard: github.rs:494.
  • Pictures branch, built by URL in the CLI: crates/fearlezz/src/action.rs:257, pushed at action.rs:613, squashed weekly at action.rs:459. The same pictures already go to the host.
  • Only read path for the agent: github.rs:666.
  • Host pain: head check and latest write not atomic (api.rs:251), shell HTML and JS as hand escaped Rust strings (pages.rs:358), nothing is ever deleted.

The feedback loop

A person marks a region on the new side, the old side or both. The agent gets the words and the picture with the region drawn on it.

$ fearlezz
...
waits  PR #24: 1 picture needs change
       demo-card  card/dark.png  after
       "The button text is cut off.
        It should fit like before."
next: fearlezz --notes  saves each note's
      pictures with the region drawn
A note as data
{
  "id": "n_7f2a",
  "head": "87c65fe",
  "check": "demo-card",
  "picture": "card/dark.png",
  "side": "after",               // before | after | both
  "region": { "x": 0.05, "y": 0.66, "w": 0.46, "h": 0.29 },
  "at": null,                    // seconds, for a film
  "words": "The button text is cut off. It should fit like before.",
  "by": "gabber235",
  "state": "open"                // open | resolved
}

Regions in fractions of the picture, so they hold at any size. On the next proof the page shows the old note next to the new picture, and the person resolves it.

Risks I see
  • Forks get no OIDC token on pull_request. Hosted proof of a fork needs a follow up run or a maintainer step, same as today.
  • Live transport on Cloudflare means Durable Objects (one per PR) with hibernating WebSockets. New to this codebase; needs a spike.
  • The UI stack. A live page with drawing wants a real frontend, not Rust strings. Separate decision, after the split.
  • Approvals by the host reverse an earlier decision ("no new trust in CI, the PR keeps the record"). The app's check run and comment keep a record; the trust moves to the host, which already holds the sign in.

Decide first: does free CI keep approvals?

Everything else follows from this. It decides whether github.rs, the 2nd workflow and the pictures branch survive in the core.

A, recommended
Free CI only proves. Changed pictures are listed in the step summary and the bundle is an Actions artifact, but they do not block. A weakening fails; an admin bypasses branch protection. The human gate is GitHub's normal PR review. All approval machinery leaves the core. Hosted adds the live page, approvals and notes.
B
Free keeps comment approvals as today; hosted adds the page on top. Two ways to approve, two authorities, and all of today's machinery stays.
C
Free CI blocks on changed pictures with no way to approve except hosted or bypass. Strong upsell, but free users get a red check they cannot clear.
